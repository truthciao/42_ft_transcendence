# Environment Configuration

## Google OAuth

Google sign-in requires your own OAuth 2.0 credentials.

1. Create or select a project in the [Google Cloud Console](https://console.cloud.google.com/).
2. Configure the OAuth consent screen and create an OAuth client ID for a web application.
3. Add the callback URL below to the authorized redirect URIs of your OAuth client.
4. Copy your credentials into `apps/api/.env`.

```env
GOOGLE_CLIENT_ID="your_google_client_id_here"
GOOGLE_CLIENT_SECRET="your_google_client_secret_here"
GOOGLE_CALLBACK_URL="https://localhost:8443/api/auth/google/callback"
```

The callback URL must match the URL configured in Google Cloud Console and the application configuration. Update it if you use a different deployment URL.

For more information, see the [Google OAuth 2.0 documentation](https://developers.google.com/identity/protocols/oauth2).

Never commit your OAuth client secret to version control.


## PostgreSQL

Generate strong, unique passwords for the PostgreSQL administrator, application, and migration accounts using OpenSSL:

```bash
openssl rand -base64 32
```

Generate a **separate password for each account** and use the corresponding value consistently throughout the configuration.

When inserting a password into a PostgreSQL connection URL, URL-encode any special characters as required. Use the original password value in the corresponding password environment variable, not its URL-encoded form.

### Administrator Connection

The administrator connection is intended for local database maintenance. The Docker network URL is used for maintenance tasks running inside the Compose network.

Replace `<POSTGRES_PASSWORD>` with the same password configured in `POSTGRES_PASSWORD` below.

```env
DATABASE_URL="postgresql://transcendence:<POSTGRES_PASSWORD>@localhost:5432/transcendence?schema=public"
DATABASE_URL_DOCKER="postgresql://transcendence:<POSTGRES_PASSWORD>@postgres:5432/transcendence?schema=public"
```

These URLs use different hosts because `localhost` refers to the local machine, while `postgres` refers to the PostgreSQL service inside the Compose network.

### Administrator Credentials

These variables configure the PostgreSQL administrator account and the database created by the PostgreSQL container.

```env
POSTGRES_USER=transcendence
POSTGRES_PASSWORD=change_me_to_a_secure_password
POSTGRES_DB=transcendence
```

Replace the example password with a strong, unique password. Ensure that it matches the password used in both `DATABASE_URL` and `DATABASE_URL_DOCKER`.

### Application Database Account

The application account is intended for API runtime operations and database seeding.

```env
TRANSCENDENCE_APP_PASSWORD=change_me_to_a_secure_password
DATABASE_URL_APP_DOCKER="postgresql://transcendence_app:<TRANSCENDENCE_APP_PASSWORD>@postgres:5432/transcendence?schema=public"
```

Replace `<TRANSCENDENCE_APP_PASSWORD>` in the connection URL with the same value configured in `TRANSCENDENCE_APP_PASSWORD`.

### Database Migration Account

The migration account is intended for database schema migrations.

```env
TRANSCENDENCE_MIGRATOR_PASSWORD=change_me_to_a_secure_password
DATABASE_URL_MIGRATOR_DOCKER="postgresql://transcendence_migrator:<TRANSCENDENCE_MIGRATOR_PASSWORD>@postgres:5432/transcendence?schema=public"
```

Replace `<TRANSCENDENCE_MIGRATOR_PASSWORD>` in the connection URL with the same value configured in `TRANSCENDENCE_MIGRATOR_PASSWORD`.

**Note:** The password placeholders in the database URLs are explanatory placeholders, not literal values. If a password contains special characters, URL-encode them when embedding the password in a connection URL.

## Initial Global Administrator

The database seed can create an initial global administrator account.

```env
SEED_ADMIN_EMAIL="admin@example.com"
SEED_ADMIN_USERNAME="admin"
SEED_ADMIN_PASSWORD="change-me"
```

Replace the example credentials before running the seed. To create the initial administrator, run:

```bash
make db-seed
```

Do not use example credentials in a production environment.

## JWT Secret

The application requires a secure `JWT_SECRET` for authentication.

Generate a random secret:

```bash
openssl rand -base64 32
```

Copy the generated value into `apps/api/.env`:

```env
JWT_SECRET="your-generated-secret"
```

Replace `your-generated-secret` with the value generated by the command above.

## Email Configuration

Email functionality can be configured using SMTP.

```env
MAIL_HOST="smtp.gmail.com"
MAIL_PORT="587"
MAIL_SECURE="false"
MAIL_USER="your-email@gmail.com"
MAIL_PASS="your-app-password"
MAIL_FROM="noreply@yourdomain.com"
```

When using Gmail, `MAIL_PASS` should normally be a Gmail **App Password**, rather than the account's regular password.

Email functionality is optional. If email is not configured, email-related features may be skipped.

## Application Base URL

This variable is used to construct links in emails.

```env
APP_BASE_URL=https://localhost:8443
```

Update this value if the application is accessed through a different base URL.

## Docker Compose Secrets

The application uses Docker Compose secrets to provide sensitive values to services without directly passing them as environment variables.

The required secret files are generated automatically by `infra/scripts/create-secrets.sh`. The script reads the corresponding passwords and sensitive values from `apps/api/.env` and writes them to files under `infra/secrets/`.

Before starting the application, ensure that `apps/api/.env` is correctly configured with the required credentials.

Start the application using:

```bash
make start
```

The Makefile automatically runs the secret-generation script before starting the services. You do not need to execute the script manually.

Keep `apps/api/.env` and the generated files under `infra/secrets/` local. Do not commit them to version control.
